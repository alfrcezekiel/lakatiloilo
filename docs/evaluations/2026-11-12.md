## Findings

### A. Spec (does it do what SPEC.md and the tickets say?)

- **[Low] The admin Reviews endpoint was described wrongly** — `docs/SPEC.md:511`
  - It still said `?…&before=` and "50 at a time"; ticket 130 replaced that with sort, Show 10/25/50 and numbered pages. Checked by comparing the spec's endpoint list with the backend's 59 routes.
  - Root cause: the endpoint line was not updated when ticket 130 changed the answer.
  - **Fixed:** the line now lists `q, show, sort, per_page, page` and the answer `{ reviews, total, page, per_page }`.
- **[Low] AGENTS.md was out of date** — section 4.4
  - It said the website has no `proxy.ts` (the admin 404 proxy exists since ticket 107) and that the backend allows exactly GET, POST, PATCH, DELETE (PUT was added for credits in ticket 132).
  - **Fixed:** both lines updated; it also now says never to delete `CORS_ORIGIN` on Vercel, only change its value (see B7).

### B. Safety, standards, UX and accessibility

- **[Medium] The navbar's Home, About, Features and Explore could not be used with a keyboard** — `src/components/DockNavbar.tsx:143` and `:170`
  - Checked in the browser: the list of focusable items did not contain them; they were `<span>`s with a mouse click handler. WCAG 2.1.1 Keyboard.
  - Root cause: plain text used as buttons (the frontend rules even described it as "clickable text").
  - **Fixed:** real `<button type="button">`s with the same look and a focus ring, on the bar and in the phone menu; the rule in `.claude/rules/frontend.md` now says anything clickable is a real button or link.
- **[Medium] The bell and account menu were the 62nd and 63rd of 69 Tab stops** — `src/components/HomePage.tsx:270`
  - They sit at the top of the screen but came after all the content. WCAG 2.4.3 Focus Order.
  - Root cause: the navbar was written at the end of the home page; it only looks first because it is fixed at the top.
  - **Fixed:** the navbar is now at the top of the page's code (nothing moved on screen). Re-checked: the bell is the 7th Tab stop.
- **[Medium] No "Skip to content" link on the traveler pages** — home page
  - The dashboard had one; keyboard users on the home page had to pass the navbar first. WCAG 2.4.1 Bypass Blocks.
  - **Fixed:** a "Skip to content" link is the first Tab stop; it shows at the top left when focused, and Enter jumps to the search box.
- **[Low] Small touch targets** — the footer's quick links (20 px tall), `src/components/LoginForm.tsx:424` "Explore as a guest" (16 px)
  - Measured with `getBoundingClientRect` at 320, 375 and 768 px. WCAG 2.5.8 Target Size (24 × 24 px). Links inside sentences are exempt.
  - **Fixed:** the footer links are at least 24 px tall; "Explore as a guest" has padding.
- **[Low] On /credits, "Back to Home" was a button inside a link** — `src/app/credits/page.tsx:34`
  - Two Tab stops for one control, and invalid nesting.
  - **Fixed:** one link styled as the same button (147 × 40 px).
- **[Low] Two headings skipped a level** — `src/components/FeaturedCards.tsx:96`, `src/components/admin/AdminCategories.tsx:147`
  - axe-core `heading-order`: "Dinagyang Festival" and "Destination categories" were level 3 with no level 2 above them. WCAG 1.3.1. The Categories one came from moving Categories to its own page (ticket 116).
  - **Fixed:** a hidden level-2 "Featured and trending" heading; the Categories headings are level 2. axe-core: 0 problems on both pages.
- **[Low] The live backend accepted calls from `http://localhost:3000`** — Vercel environment of the backend project
  - Checked with `curl -X OPTIONS` and an `Origin` header. The risk is low (the login token is sent by the page, not as a cookie), but anyone's local copy of the site could call the live backend.
  - **Fixed by the team:** `CORS_ORIGIN` on the live backend is now only `https://lakat-iloilo.vercel.app`. While doing this, the variable was first deleted, and the live backend answered 500 on every request (it refuses to start without `CORS_ORIGIN`); the team re-added it and redeployed. Re-checked: the live site is allowed, `localhost:3000` and other sites are refused, places answer 200.
- **[Low] An unknown API address answered "Cannot GET /v1/nothing"** — the framework's own wording
  - **Fixed:** `backend/src/unknown-route.filter.ts` answers "We couldn't find that address."; every other 404 keeps its own sentence (checked: an unknown destination still says "We couldn't find that destination.").
- **[Low] Forgot password, submitted empty, did not move the focus to the email field** — `src/components/ForgotPasswordForm.tsx`
  - The message showed and was linked to the field (WCAG 3.3.1 was met); moving the focus helps keyboard users.
  - **Fixed:** the focus moves to the email field. Nothing is sent.
- **[Low] No Content-Security-Policy header on the live site**
  - The other headers are present (nosniff, Referrer-Policy, HSTS, X-Frame-Options DENY). Already parked in `docs/LATER.md`; not changed.

## What was checked, how, and what was NOT checked

**Checked:**
- Static: `npx tsc --noEmit`, `npm run lint`, `npm run build`, backend `npx tsc --noEmit -p tsconfig.json` — all pass.
- Functions (reading the code): `TravelerTransactions` checks the login, then runs each write as that person in one transaction, so Row Level Security decides; no write goes around it (the direct queries are reads); every SQL text that is built uses fixed text, and input travels as `$1`, `$2`; Realtime is a doorbell only (`ring` never reads the row) and never listens to `review_reports`; `src/proxy.ts` lets the backend decide who is an admin.
- API (`curl`, localhost and live): 47 checks — reads 200 with the right shape; every write and admin endpoint 401 logged out and with a fake login; unknown and badly formatted ids 404 with the spec's sentence; bad input 400 with a "Please …" sentence; injection-shaped input answers normally; `/near` sorted, a missing `lat` or a bad radius 400; no 500s. One expected mismatch: a review posted with a fake login and an incomplete form answers 400 (the form is checked first); a complete one answers 401. Speed: under 0.4 s, except checking a fake login with Supabase (about 1 s).
- Privacy: reviews and traveler profiles carry display names only; the only emails are the hotels' own front-desk addresses; no token, `service_role` or authorization status in any public answer.
- Middleware: CORS (allowed origins only), the backend's startup check for `CORS_ORIGIN`, security headers on the site and the backend.
- Database (reading the SQL files): Row Level Security on every table, with policies for each action; the newer tables were proven in rolled-back tests during the rounds (054, 055). Secret scan: no key values, no `.env` files tracked.
- Browser (localhost, reading only): axe-core 4.10.2 (loaded into the tab only, not added to the project) on 18 pages — home, two place pages, Photo credits, log in, forgot password, a traveler profile, an unknown traveler, an unknown page, and every dashboard page; one main heading and `<main>` on each; no sideways scrolling at 320, 375 and 768 px; touch-target sizes; a keyboard pass with Tab on the home page; the search box with the keyboard (combobox, arrow keys, "3 suggestions" announced, Escape closes); forgot password submitted empty; the review form's labels and the Helpful buttons' pressed state.

**Confirmed by the team (2026-11-12):** the log-in and sign-up forms show the right messages; logged out, a traveler is asked to log in to write a review; logged in, a traveler can post a review with a photo, like, reply, edit, delete and report; at 200 % zoom the home page and a place page have no sideways scrolling; a screen reader on Windows, Linux and Android reads out the place page and the review form (stars, text box, photo and the "posted" message). After the fixes, on localhost: one Tab shows "Skip to content" at the top left; Tab then reaches Home, About, Features and Explore, then the bell and the account menu; the phone menu still works; on /credits, "Back to Home" goes to the home page.

**Not checked by the agent:**
- Log in and sign up in the browser (the browser was signed in as an admin, and signing out would have ended the team's session) — confirmed by the team instead.
- Any real write (reviews, likes, replies, reports, admin actions) — confirmed by the team instead.
- A screen reader run by the agent itself (the team ran one on Windows, Linux and Android instead). Apple's VoiceOver (Mac, iPhone) was not tried.
