# Performance evaluation (k6), website and `/api` proxy — 2026-11-21

**Tool:** Grafana k6 v2.4.0, run locally (no Grafana Cloud) · **Scripts:**
`performance/k6/lib/site.js`, `scenarios/site-smoke.js` and
`scenarios/site-load.js` (new today) · **Ran from:** the team's Ubuntu
laptop · **Requests:** public GETs only (pages, and data through the
website's `/api/v1/...`), no logins, no writes. Every request also reaches
the **hosted** Supabase database.

**Why new tests:** since tickets 151–153 the browser never calls the
backend. It calls the website's `/api`, which passes the call on, and since
ticket 156 every page is built per visit with a fresh CSP nonce. The older
k6 tests (`perf:smoke`, `perf:load`) call the backend on port 5000
directly, so they could not measure that path or check its security.

## Verdict

**Passed, on localhost and on the live site.** Up to 20 travelers at once
got every page and data answer without a single error, 95 % of pages in
under 0.8 s, and **every one of the 15,327 security checks passed** under
load: an enforced CSP with a new nonce on every page, and the backend's
address and headers hidden on every answer. Nothing needs fixing before
the demo.

## What changed in the scripts today, and why

- **Warm-up in `setup()`:** the first site smoke failed (pages 849 ms ✗)
  because the home page's first visit after the website starts took 0.85 s
  (later visits 0.3 s), and a 40-second smoke has only about 9 page
  visits. `setup()` now opens each page once first. The limit stays 800 ms.
- **Proved able to fail:** against a pretend site with a report-only
  policy, a fixed nonce, `'unsafe-inline'`, `X-Powered-By`, an open CORS
  header and the backend's address in its answers, all 8 security checks
  failed and k6 exited with a failure code.
- **Guard:** `site-load.js` refuses any address other than localhost
  unless `-e LIVE_OK=yes` is passed (checked: it stops before the first
  request on the live URL).

## Breakpoint test added (agent, same evening)

For the "more than 150 travelers" item above, there is now a test that
finds where the app breaks: `breakpoint.js` (backend) and
`site-breakpoint.js` (website), with shared code in
`performance/k6/lib/breakpoint.js`.

- **What it does:** one steady ramp from 0 to 400 travelers over 20
  minutes (about 20 more a minute). k6 stops it by itself as soon as the
  app counts as broken, using the same limits as stress: more than 5 %
  errors, or p(95) over 1.5 s, or (website) any security check failing.
  The difference is that here **every** limit stops the test. Change
  the ramp with `-e BREAK_MAX_VUS=` (160–1000) and `-e BREAK_MINUTES=`
  (5–60).
- **Reading it:** `vus ... max=` in the summary is how many travelers
  were on when it stopped. The app broke a little before that, because
  k6 judges p(95) over the whole run so far. If every line is ✓ and it
  ran the full 20 minutes, the app did not break up to 400.
- **Commands:** `npm run perf:breakpoint` and
  `npm run perf:site:breakpoint` (localhost; for the website, use
  `npm run build` + `npm start`). On the live URLs:
  `npm run perf:live:breakpoint -- -e LIVE_OK=yes` and
  `npm run perf:live:site:breakpoint -- -e LIVE_OK=yes`. Those last two
  only after the whole team agrees, at a quiet time. They are the
  heaviest traffic this project sends to Vercel and the hosted database,
  and Vercel's firewall may start refusing what looks like an attack.
- **Checked, without sending traffic to anything real:** `k6 inspect`
  reads both files (20-minute ramp to 400, every limit set to stop the
  test). Both refuse a live URL without `-e LIVE_OK=yes`, before the
  first request. Out-of-range settings are refused with a clear message.
- **Proved able to stop:** against a pretend backend on the laptop
  (`127.0.0.1:3997`, which answers normally for 70 s and then fails
  every request), the breakpoint test stopped itself at 73 s with 39
  travelers on: "thresholds on metrics 'http_req_failed' were crossed …
  stopping test prematurely", failure code 99.
- **Not run on the real app.** The team starts it.
