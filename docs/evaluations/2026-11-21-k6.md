# Performance evaluation (k6), website and `/api` proxy — 2026-11-21

**Tool:** Grafana k6 v2.4.0, run locally (no Grafana Cloud) · **Scripts:**
`performance/k6/lib/site.js`, `scenarios/site-smoke.js` and
`scenarios/site-load.js` (new today) · **Ran from:** the team's Ubuntu
laptop · **Requests:** public GETs only (pages, and data through the
website's `/api/v1/...`), no logins, no writes. Every request also reaches
the **hosted** Supabase database.

**Why new tests:** since tickets 151–153 the browser never calls the
backend. It calls the website's `/api`, which passes the call on, and since
ticket 156 every page is built per visit with a fresh CSP nonce. The older
k6 tests (`perf:smoke`, `perf:load`) call the backend on port 5000
directly, so they could not measure that path or check its security.

## Verdict

**Passed, on localhost and on the live site.** Up to 20 travelers at once
got every page and data answer without a single error, 95 % of pages in
under 0.8 s, and **every one of the 15,327 security checks passed** under
load: an enforced CSP with a new nonce on every page, and the backend's
address and headers hidden on every answer. Nothing needs fixing before
the demo.

**Caveats:**

## Live smoke in detail (team)

All 12 pages and routes were visited at least once (19 visits). Pages
p(95) 293 ms and `/api` p(95) 323 ms: the live website is **faster than
localhost** because it runs in Mumbai, next to the backend and the
database (since `d1137f1`). The slowest request (982 ms) was one of
`setup()`'s warm-up visits, which the thresholds do not count, as
intended: the first visit after a quiet spell fills the website's caches.

## What changed in the scripts today, and why

- **Warm-up in `setup()`:** the first site smoke failed (pages 849 ms ✗)
  because the home page's first visit after the website starts took 0.85 s
  (later visits 0.3 s), and a 40-second smoke has only about 9 page
  visits. `setup()` now opens each page once first. The limit stays 800 ms.
- **Proved able to fail:** against a pretend site with a report-only
  policy, a fixed nonce, `'unsafe-inline'`, `X-Powered-By`, an open CORS
  header and the backend's address in its answers, all 8 security checks
  failed and k6 exited with a failure code.
- **Guard:** `site-load.js` refuses any address other than localhost
  unless `-e LIVE_OK=yes` is passed (checked: it stops before the first
  request on the live URL).

### What it means for a traveler on demo day

Even if 150 people open the site at once, or 100 arrive in one burst
after a post is shared, every page and data answer arrives, almost all
of them in under 0.3 s on the live site. After half an hour of steady
use nothing got slower (the soak p(95) matches the short tests), so
nothing leaks or piles up. The security headers did not slip once under
load.

### Worth knowing (not failures)

- **The live site is faster than localhost** (pages 0.28 s against
  0.57 s under stress). The live website, backend and database all run
  in Mumbai. The laptop's local website and backend reach that database
  from the Philippines.
- **The slowest single requests:** one live backend answer took 26 s
  during `perf:live:load`, and one local `/api` answer took 7 s during
  `site-soak`. Each is one request out of thousands. p(95) and the
  error rate did not move, so it was a single delay (likely a Vercel
  function starting fresh, or a network hiccup), not a pattern. The
  summaries do not say which route it was. If it shows up again, run
  that test with `--out json=…` to find the route.
- **Website answers are heavier than data answers:** about 28 KB each in
  site stress (500 MB over 17,861 requests), against about 9 KB for a
  backend answer. That is the page HTML, built per visit for the nonce
  CSP. It is not a problem at this size.
