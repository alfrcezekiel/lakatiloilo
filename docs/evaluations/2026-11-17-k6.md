## Verdict

**Passed.** The backend answered all 3,240 requests from up to 20
travelers at once without a single error, and 95 % of answers came back in
under 0.3 s. That is well inside the 0.8 s limit. Nothing needs fixing
before the demo.

## Stress and spike (2026-11-18, localhost)

**The app never broke. It slows down when it is very busy.** Every request
in both tests succeeded (0 of 16,892 failed, every answer was 200 and
JSON). Only the speed limit was crossed: 95 % of answers came back within
about 2 s, against a limit of 1.5 s. That limit was not loosened (see
`.claude/rules/testing.md`).

- **Breaking point (speed, not errors):** with 20 travelers, answers take
  0.2–0.3 s. With 150, the backend cannot go past **~26 requests a
  second**, so the rest wait in line (median 0.65 s, p(95) 2.1 s, slowest
  2.6 s). There were still no errors at 150.
- **Spike:** a jump from 5 to 100 travelers in 10 seconds was absorbed
  with **no errors**, but answers slowed to about 2 s during the rush.
  Recovery afterwards is not visible in a summary. To see it, re-run with
  the web dashboard and watch the last 2 minutes.

**Cause: the database connection pool (confirmed, see below).** The backend sets no pool
size, so TypeORM uses node-postgres' default of **10 connections**, through
Supabase's pooler (port 6543) over the internet. 10 connections ÷ about
0.3 s per round trip ≈ 25–35 requests a second, which matches the ceiling
measured. This is a reading of the numbers, not yet proven by changing the
pool size.

**What it means for demo day:** fine. 20 pretend travelers, each clicking
every 1–3 s, are already busier than a demo audience, and that passes
easily. The slowdown starts well above that.

**On the live site it will differ.** Vercel starts more copies of the
backend when it is busy, each with its own pool, and runs closer to
Supabase. These localhost numbers describe one laptop and one backend.

## Soak, clean run (2026-11-18, 09:34–10:08, localhost): no slowdown over time

Nothing else ran: no other tests, no file edits and no restarts. The
backend was on the 20-connection pool, with `DATABASE_POOL_MAX=20` now
written in the local `backend/.env`. Command:
`K6_WEB_DASHBOARD=true K6_WEB_DASHBOARD_EXPORT=performance/k6/results/soak-report.html npm run perf:soak -- -e SOAK_MINUTES=30`

- **All limits passed:** p(95) 290 ms, **0 of 17,242 failed**, checks
  100 %, and **no `connection refused`**.
- **The answer to the soak question: no.** Response times did not creep up
  over the run. From the dashboard report, in 10-second slices grouped
  into 5-minute blocks:

| Minutes | Requests | Average | p(95) | Failed |
|---|---|---|---|---|
| 0–5 (ramp up) | 2,150 | 228 ms | 288 ms | 0 |
| 5–10 | 2,699 | 227 ms | 288 ms | 0 |
| 10–15 | 2,684 | 226 ms | 287 ms | 0 |
| 15–20 | 2,680 | 243 ms | 288 ms | 0 |

| 25–30 | 2,696 | 225 ms | 289 ms | 0 |
| 30–35 (ramp down) | 1,642 | 230 ms | 289 ms | 0 |

  p(95) was 288 ms both at the start and at the end of the hold. A leak
  (memory, connections never released, a cache that keeps growing) would
  show as a steady climb, and there is none.
- **Two single slow answers**, each one 10-second slice: 1.6 s at the very
  start (the backend opening its database connections), and 5.8 s at
  about 15 min, with normal minutes on both sides. Probably a brief
  hiccup on the internet path to Supabase; the report can't prove which.

  Open it in a browser to see the charts.

## Soak (2026-11-18, 08:12–09:16, localhost): passed, but not a clean run

All three limits passed: p(95) 621 ms (limit 800), 0.32 % failed (limit
1 %), and checks 99.67 % (limit 99 %). But the hour was not a fair
measurement, so it **cannot answer the soak question** ("does the app slow
down over time?"):

- **All 105 failures were backend restarts caused by the agent's edits**,
  not the app failing. Each one was `connection refused` (nothing
  listening on port 5000), in 4 bursts of a few seconds that match the
  times `backend/src/database/database.module.ts` was saved or the backend
  was restarted for the pool experiment: 08:32:26, 08:47:05, 09:12:52 and
  09:13:14 (the file's last save time, exactly). After each restart the
  backend answered again within seconds, without help.
- **Two stress tests ran at the same time** (08:33–08:42 and 08:57–09:06),
  adding up to 150 more pretend travelers. That pushes p(95) up.
- **The pool changed three times** during the hour (10 → 20 → 10 → 20).

**Lesson for next time (agent):** don't save backend files or restart the
backend while a team member may be running a long test. Ask first.

**To answer the soak question:** run it again with nothing else
happening. No other tests, no edits to backend files, and the backend
already on the 20-connection default. Use `-e SOAK_MINUTES=30` for a
34-minute run if an hour is too long. To see whether answers get slower
over time, add the web dashboard and keep its report:
`K6_WEB_DASHBOARD=true K6_WEB_DASHBOARD_EXPORT=performance/k6/results/soak-report.html npm run perf:soak`

### Pool-size experiment (2026-11-18, localhost)

`backend/src/database/database.module.ts` reads the pool size from
`DATABASE_POOL_MAX`. During the test, unset still meant 10.
For the test, the local `backend/.env` had `DATABASE_POOL_MAX=20` (removed
again afterwards), and the same stress test ran again:

| | Pool 10 | Pool 20 |
|---|---|---|
| Requests | 14,208 (26.2/s) | **18,211 (33.6/s)**, +28 % |
| Median | 645 ms | **192 ms** |
| p(95) | 2,086 ms ✗ | **299 ms ✓** |
| Slowest | 2,614 ms | 1,090 ms |
| Failed | 0 % | 0 % |

**Confirmed:** with 20 connections, 150 travelers get answers as fast as
20 did before. The wait for a free database connection was what slowed the
backend. Changing only the pool size made the difference (the local SQL
logging was on in both runs).

**Confirmed by the team after the change:** their own stress run on the
new default passed every limit (p(95) 469 ms, median 223 ms, slowest
1.87 s, 0 of 18,011 failed, 33.3 requests/s). That's slightly slower than
the agent's 299 ms run, which is normal variation on a laptop that is
also running the dev servers, and far from the 2.1 s on 10 connections.

**Decided (team, 2026-11-18): the default is now 20**, on localhost and
on Vercel once pushed. `DATABASE_POOL_MAX` can still lower or raise it
(1–50). On Vercel each running copy of the backend has its own pool, so
copies × 20 must stay under the Supabase plan's connection limit. Lower
it there if Supabase ever refuses connections.

**Other next steps (not done):**
1. Re-run the spike with `K6_WEB_DASHBOARD=true` to see the recovery.
2. Run the soak test (64 min, or 34 with `-e SOAK_MINUTES=30`).

## What it means for demo day (load test, 2026-11-17)

- **20 pretend travelers at once is more than a demo audience.** Each one
  makes a request every 1–3 seconds. A real person spends much longer on
  a page, so 20 of them are a lot busier than 20 real visitors.
- **More travelers didn't make it slower.** p(95) with 20 travelers
  (297 ms) was *lower* than with 1 traveler (476–519 ms). With only 16
  requests, the smoke result was pulled up by the slow first request,
  while the backend was still opening its database connection. With
  3,240 requests, that first request hardly counts.
- **Most of each answer's time is the trip to the hosted database.** The
  backend runs on the laptop, but Supabase is in the cloud. A typical
  0.2–0.3 s is mostly that round trip, not slow code.

## Likely causes and next steps

- **Nothing to fix.** No route is close to the limit.
- The slowest normal routes are the single-place and reviews routes
  (about 0.3 s). They do the most work: a place with its details, or
  reviews with photos, likes and replies. If a later round makes them
  slower, check their queries first, and add an index with `/sql-change`
  if needed.
- The setup lookup (885 ms, once per test) counts towards p(95). It makes
  short smoke runs look a little slower than the app really is. Changing
  that is optional.

terminal is the easier place to read it.
