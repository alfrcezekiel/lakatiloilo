## Finding: the live backend is far from its database

| Piece | Region |
|---|---|
| Database (Supabase pooler) | `ap-south-1`, Mumbai |
| Live backend (Vercel function) | `iad1`, Washington D.C. (from `x-vercel-id: sin1::iad1::…`) |
| Travelers | enter Vercel in `sin1`, Singapore |

One warm read takes **~0.55 s on the live API** and **~0.095 s through the
local backend**, which reaches Mumbai directly. Every database question
crosses from the US to India and back, and a request asks several. This
predates today's push.

**Fix (team decision, 2026-11-18): the backend runs in `bom1` (Mumbai)**,
next to the database. `backend/vercel.json` has `"regions": ["bom1"]`,
which overrides the project setting (`iad1`) on every deploy (the
backend project's root directory is `backend/`). **It takes effect on the
next deploy.** Then re-run the k6 smoke against the live API: it should
come close to the local numbers.

**Live since `69342f5` (2026-11-18), checked:** `x-vercel-id` now shows
`sin1::bom1::…`. Warm reads take **0.21–0.27 s** (was ~0.55 s; the odd
0.5–0.6 s is a fresh function instance). k6 smoke on the live API:
**p(95) 377 ms and 226 ms**, 0 % failed, limit 800 ms ✅ (was 920–975 ms ⚠️).
Refusals unchanged: no login 401, fake login 401, admin 401, bad id 404.

**The website follows (team decision, 2026-11-18):** the website (Vercel
project `amor-phinma-builder-template`) also ran in `iad1`. Place pages
are drawn on its server, which asks the backend for the place: one trip
from the US to India per page. A `vercel.json` at the repo root now says
`"regions": ["bom1"]` for the website too (the backend project reads only
`backend/vercel.json`). It takes effect on the next deploy; then
`x-vercel-id` on a page should end in `::bom1::…`.

**Live since `d1137f1`, checked:** pages show `sin1::bom1::…` (about 30 s
after the push). A place page's first byte went from **0.61–0.70 s** to
**0.26–0.31 s** once warm (the first request after the deploy took 1.1 s).
Lighthouse, place page on a phone, two runs: Performance 82 / 80, LCP
3.07 / 3.36 s (about as before: the LCP is the place photo, not the
server), but **TBT 488 / 466 ms**, above the 200 ms budget and the earlier
runs. TBT is work in the phone's browser, which the region cannot change,
so this is a separate, still open question.

**Looked into (same day):** the high TBT is **on every page, not the place
page**. A fresh phone run gave home 572 ms (it was 187–217 ms this
morning), place 540 ms, login 203 ms. No change since this morning adds
JavaScript (one swapped `<img>` for `<picture>`, then two region
settings). The busy work is the same as before: React starting the page

the Supabase client. What did change: **the laptop running Lighthouse
was on battery** (charger unplugged, CPU at ~1.7 GHz on "powersave").
Lighthouse runs the page on the computer's own CPU and then slows it 4×
to imitate a phone, so a slower laptop means a higher TBT. 

**Confirmed with the charger plugged in** (CPU ~3.9 GHz, Lighthouse's
speed score for the laptop 2972 instead of ~1530), two phone runs:

## Fixed: the background photo on phones (2026-11-18, live since `69342f5`)

Checked on the live site: a 412 px phone gets the 960 × 2400 portrait crop
(**107 KB**) on home and login; a 1350 px laptop gets the 1920 px photo
(**174 KB**).

The home hero, login pages and admin dashboard downloaded the same
**1920 × 1280 JPEG (317 KB)** on every screen, including a 412 px phone.
A plain smaller copy would have looked blurry: the photo fills a *tall*
box (`object-cover`), so a wide photo has to be enlarged to fill the
height. Now `src/components/HeroBackground.tsx` (used by all three) gives:

| Screen | Before | After |
|---|---|---|
| Phone (412 px, up to 767 px wide) | 317 KB, landscape JPEG | **107 KB**, portrait crop 960 × 2400 (AVIF), **−66 %** |
| Laptop (1350 px) | 317 KB | **174 KB**, 1920 px (AVIF), **−45 %** |

Checked on home and login at both sizes: the right file loads, the photo
fills its box exactly as before, and the phone crop has slightly more
pixels than the screen needs, so it is sharp. ESLint, Vitest (76),
Playwright (59) and the build pass.
