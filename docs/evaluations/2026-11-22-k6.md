# Breakpoint test (k6), website on localhost and live — 2026-11-22

**Tool:** Grafana k6 v2.4.0, run locally · **Script:**
`performance/k6/scenarios/site-breakpoint.js` (new, see
`2026-11-21-k6.md`) · **Ran from:** the team's Ubuntu laptop (12 CPU
threads), just after midnight · **Target:** `http://localhost:3000`, a
production build (`next start`), with the backend on `localhost:5000`
· **Requests:** public GETs only. Every page also reaches the hosted
database.

## Verdict (both runs)

**Live site: did not break at 400 travelers at once.** 0 errors in
111,017 requests, pages p(95) 0.26 s, every one of 364,022 security
checks passed. **One laptop: reaches its limit at about 200–229.** The
difference is the hosting: Vercel adds copies of the website as
traffic grows, and the laptop runs one. Details of each run below.

## Run 1: one laptop (`npm run perf:site:breakpoint`)

**The test worked as designed: it found the breaking point.** On one
laptop, the website reaches its limit at **about 200–229 travelers at
once** (46 requests a second). There, 95 % of pages took longer than
1.5 s, and k6 stopped the test by itself. It is not a script error and
not a bug in the app. Even at the limit, nothing failed: 0 errors in
31,890 requests, and all 158,274 checks passed, including every security
check.

The line that looked like a crash,
`ERRO[0690] thresholds on metrics 'http_req_duration{kind:page}' were crossed; … stopping test prematurely`,
is how k6 says "I stopped on purpose, because a limit broke." Exit code
99 means the same.

## The result

| Measure | Value | Plain words |
|---------|-------|-------------|
| Stopped after | 11 min 30 s of the 20-minute ramp | the ramp adds about 20 travelers a minute |
| Travelers on when it stopped | **229** | the limit is a little lower: k6 judges p(95) over the whole run, so it notices late |

| Pages p(95) | **1.52 s ✗** (limit 1.5 s) | the limit that broke |

| Security checks | 100 % ✓ | the CSP and hidden backend held at the limit |
| Slowest request | 5.3 s | a page near the end |

## Root cause: one website process can only use one CPU core

Measured on the same laptop after the run, with single requests (no
load):

| Request | Website CPU per request | Backend CPU per request |
|---------|-------------------------|-------------------------|
| Home `/` | **69 ms** | 22 ms |
| A place page | 23 ms | 9 ms |
| `/login` | 11 ms | 0 |
| `/api/v1/destinations` | 6 ms | 8 ms |
| Average over the site smoke's mix | 26 ms | 17 ms |

- `next start` runs the website as **one Node.js process**, and one
  Node.js process does its work on **one CPU core**, however many the
  laptop has. One core gives 1,000 ms of work a second.
- The test's travelers open home 4 times out of every 10 visits. At 46
  requests a second, the website needs about 1,200 ms of work every
  second. That's more than one core can do, so requests start waiting in
  line, and pages slow past 1.5 s. That is exactly where the test
  stopped.
- A CPU profile of home (a copy of the website on port 3001, 35 visits)
  shows no single slow spot in our code. The time is spread across
  Next.js rendering the page (navbar, hero, sections, icons) and packing
  the place data for the browser. There is no one-line fix.

**On the live site this limit does not apply in the same way.** Vercel
runs the website as functions and starts more copies when traffic
grows, so the work is shared across many cores. That is why live stress
at 150 travelers stayed at 0.28 s (2026-11-21), while the laptop slowed
down around 200. The laptop result answers "how much can one website
process take?", not "how much can the live site take?".

## What changed

- **Nothing in the app, and no limit loosened.** The 1.5 s limit is
  doing its job.
- **The test now says what happened in plain words** when it stops
  (`performance/k6/lib/breakpoint.js`, `teardown()`). For example:
  `BREAKPOINT RESULT: the app reached its limit at about 229 travelers
  at once, after 11.5 of 20 minutes. This is the answer the test looks
  for, not a script error …`. If it never breaks, it says it held up to
  the maximum. Checked against a pretend failing backend on the laptop:
  it printed "about 38 travelers" where k6 counted 39, then stopped with
  code 99.

## For demo day

20–50 people at once is far below 200, even on one laptop. Nothing needs
fixing for the MVP.

## Run 2: the live site (`npm run perf:live:site:breakpoint -- -e LIVE_OK=yes`)

Run by the team with the whole team's agreement, against
`https://lakat-iloilo.vercel.app` (commit `4b07824`; ticket 158 was not
pushed yet, which does not change server speed). The full 20-minute ramp
from 0 to 400 travelers.

**Verdict: the live site did not break. It held 400 travelers at once
without slowing down.** The test printed:
`BREAKPOINT RESULT: the app did not break. It held up to 400 travelers at once (20-minute ramp).`

| Measure | Live, ramp to 400 | Live stress, 150 (2026-11-21) | Laptop breakpoint (run 1) |
|---------|-------------------|-------------------------------|---------------------------|
| Travelers at the end | **400** (399 measured) | 150 | 229, stopped |
| Requests per second | **92** | 34 | 46 |
| Pages p(95) | **259 ms ✓** | 292 ms | 1,520 ms ✗ |
| `/api` p(95) | **188 ms ✓** | 206 ms | 1,070 ms |
| Pages median | 193 ms | 210 ms | 401 ms |
| Errors | **0 of 111,017 ✓** | 0 of 18,533 | 0 of 31,890 |
| Security checks | **364,022 of 364,022 ✓** | 61,038 of 61,038 | 100 % |
| Slowest request | 1.03 s | 1.78 s | 5.3 s |
| Data received | 3.0 GB | 513 MB | 869 MB |

**What it shows:**

- **More travelers did not make the live site slower.** At 400 travelers
  and 92 requests a second, pages p(95) was 259 ms, a little faster than
  at 150 (292 ms). Vercel started more copies of the website as the
  traffic grew. That is exactly the difference from the laptop, which
  has one website process on one CPU core.
- **The 1.5 s limit was never close:** the slowest single request in 20
  minutes was 1.03 s.
- **Security held under the heaviest load yet.** 364,022 checks:
  enforced CSP with a fresh nonce on every page, and the backend's
  address and headers hidden on every `/api` answer.
- **Vercel's firewall did not block the test** (0 failed requests).
- **The live breaking point is above 400**, so it is still not known. For
  this MVP that is a good answer: 400 people at once is 8–20 times the
  expected demo-day crowd.

**Cost to know about:** this run downloaded 3.0 GB from Vercel in 20
minutes. On Vercel's free plan (about 100 GB a month), a few runs like
this use a noticeable share. Do not repeat it casually, and check the
project's Usage page in the Vercel dashboard.

## What was fixed

Nothing in the live run needed fixing: every threshold passed. The only
fix in this round is the plain `BREAKPOINT RESULT` line (above), which
worked in the live run too.
